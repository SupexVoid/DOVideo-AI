# 文本剪辑：实现决策与面试追问记录

只记录实际需求、实现和验证。用户提出课程回看与博主初剪的共同需求；AI 辅助代码、排查及测试。尚未发生的用户使用、节省时长或平台接入不作为成果。

## 2026-10-20：为什么换转写服务

**问题：** 原 ASR 返回全文，没有每句话起止时间；无法可靠地把“删一句文字”映射为视频区间。

**候选：** Whisper 兼容在线服务、百炼 Paraformer、本地模型。用户倾向国内服务，已自行开通北京地域 API Key，并确认 Paraformer 免费额度页面。最终选择 `paraformer-realtime-v2`，直接在后台发送本地音频；不用开放本机 MinIO 给云端下载。沿用 OkHttp，无须新增 SDK。

**真实成本：** 需要实现 WebSocket 启动、音频流、最终句段、结束确认、超时与取消。实时模型不意味着必须做直播；我们在有界后台任务中处理录制好的音频。

**可能追问：** 为什么普通转写不能剪视频？为什么不让大模型估计时间？为什么不通过 URL 提交本地视频？

**验证：** 适配器协议测试与实际短视频识别待记录，不把预制字幕当作识别成功。

## 2026-10-20：一份结果服务总结和剪辑

**问题：** 原文字入口、AI 分析和新编辑器各自转写会重复请求，且纯文本与时间轴可能不一致。

**方案：** 已完成的自动时间轴作为共用来源；原文字面板读取其全文，AI 上下文使用其真实句段。字幕导入仍是独立来源，不冒充 ASR。失败的新尝试不应删除原来成功文档，编辑方案继续引用原字幕版本。

**缓存取舍：** 原 VideoContext 可能保存的是 60 秒粗粒度转写，不可直接作为新句段精度的证据。带时间转写模式下核对旧上下文与真实句段，不一致则重建；暂不进行跨媒体上下文复用，代价是少量重复 OCR，避免扩张检查点架构。

**可能追问：** 怎样避免多个入口重复识别？数据库中已有文字为什么还要检查时间？失败重试会不会破坏旧方案？

## 当前产品边界与后续需用户决定的方向

- 本轮保留原台词，不自动改写、不删除语气词，不根据“excuse me”自动判断有效对话。
- 按识别服务的最终句段展示；整句段选择。任意文字改写不会生成新的声音。
- 总结默认理解原视频完整内容；剪辑选段仅影响成片。未来若增加“仅总结保留内容”，需要用户确认入口与默认行为。
- 句段之间的停顿、开场画面是否保留，会影响自然程度；先展示真实切点并验证，待真人素材反馈后决定是否增加边界微调或停顿策略。
- “两小时变十分钟”是需求目标，尚无真人素材对比，不作为实测指标。

## 真实服务首次验证（2026-10-20）

已使用本地保存的 Key 直接调用百炼处理 37.320 秒自制合成语音，返回 8 个真实最终句段；没有读取预制 SRT。返回中存在正常识别错误（例如“再排除”识别为“在排除”）与自动标点差异，不宣称文字完全准确。

**新暴露的产品取舍：** 服务句段之间有约 0.42 秒空隙，仅裁剪语音区间会压缩自然停顿。已向用户提问默认保留自然停顿还是去掉空隙；推荐保留相邻保留句之间的停顿。该选择待答复，期间不改变既有裁剪规则、不伪造 ASR 时间。

**面试追问：** 服务给了时间戳为什么还不够？一句话结束与一个剪辑点的边界是同一回事吗？如何区分识别时间与编辑区间？

## 页面恢复问题（2026-10-20）

**复现：** 识别任务在后台处理时关闭编辑器，再从资料库重新打开，页面只有等待提示，却不查询状态，后台完成也不会显示。

**处理：** 区分“创建新任务”和“观察已有任务”。上传入口可提交新任务；普通重新打开只恢复已有任务轮询，不再请求模型识别。关闭或导入新字幕时清理旧查询，防止迟到结果覆盖新时间轴。

**验证：** 新增两个失败回归后修复，完整前端 63 项测试与构建通过，独立复审通过。

**可能追问：** 前端关闭了，后台任务是否取消？恢复页面为什么不能再提交一次？任务状态为什么要存在数据库？

## 缓存迁移：不是只换一份文字（2026-10-20）

**复现：** 原 AI 流程既缓存共享 VideoContext，也按分析目标缓存 plan、执行草稿、Critic 和结果，长视频另存分块。如果只把上下文换成精细句段，Agent 仍可能从旧 Critic 直接返回旧结果；目标 A 完成迁移后，目标 B 也可能错误复用旧产物。旧分块还会带回粗粒度证据。

**选择：** 在同一视频的上下文锁中，发布新上下文前失效相关机器生成的派生产物与分块。保留用户反馈、待应用的修订请求、字幕和剪辑方案。Redis 清理不依赖可能已过期的目标索引；失败时不发布新上下文，重试仍能识别迁移未完成。

**权衡：** 选择一次性重建，代价是重新生成分析派生产物；相比给全部旧检查点增加来源版本迁移，修改面更小。向量索引写入失败时回退本地检索，避免旧远端分数影响新分块排序。

**可能追问：** 多层缓存为什么不能只删除最外层？哪一份是真源？清到一半失败怎么办？用户反馈为什么不能和缓存一起清理？

**验证：** 已实际复现旧终态 Critic 被返回；新增回归覆盖多目标产物、分块及向量更新失败。最终测试结果见验证记录。

**后续索引问题：** 清理远端向量失败后，仅第一次请求降级还不够，下一次读取缓存分块也不能默认索引已经可用。每次使用缓存分块前重写当前向量，确认成功且至少有一个有效向量后才启用远端评分；否则使用当前文字的本地检索。代价是每次缓存检索增加一次索引写入，不重新调用 Embedding 或语言模型。回归覆盖连续两次查询与全空向量批次，避免把无操作当作成功。

**最终验证：** 后端完整 139 项、前端完整 63 项及构建通过，独立缓存复审通过。真实合成视频完成百炼转写、保存、导出、下载，浏览器播放至 26.140 秒结尾。真人识别、切点听感、文本模型实际总结仍不作为已验收经历。

## 2026-10-20：从手动删段扩展到 AI 智能选段

**需求与选择：** 用户要求复用视频与文字链路，让模型根据目标推荐保留内容。第一版选择“AI 推荐 → 用户预览确认 → 已有导出”，没有让模型编造时间，也没有加入另一家视频剪辑服务。实际调用沿用硅基流动 DeepSeek-V3.2，处理现有百炼句段；后端用真实 ID 映射时间。

**实际结果：** 同一段自制合成视频的 8 句文字，按保留二分查找讲解的目标推荐第 2、3、4 句，分别说明主题、前提和基本步骤。预计 14.120 秒，真实导出 14.160 秒并在浏览器播放至结尾。不能据此声称真人英语对话识别精度或节省剪辑时长。

**难点一：推荐不能覆盖用户劳动。** 生成和应用是两个动作；只有用户明确应用才修改草稿，保存、导出继续单独确认。模型响应迟到、切换视频或登录、用户在等待时改了选段，都不能静默覆盖。关闭后恢复的推荐额外要求确认替换；相关前端回归覆盖这些竞争情形。真实验证应用后未保存时数据库仍为原先 6 句，保存后才成为 3 句的新版本。

**难点二：限制无效或失控的输出。** 返回 JSON 必须只包含当前批真实句段 ID 和理由，后端拒绝无效编号，不采用模型返回的时间。长稿在句数和文字长度双重限制下分批，正常重叠 2 句；字数边界放不下时降低重叠，保证向前推进。某批失败不发布局部成功，单任务最多 20 批、8 分钟，模型沿用有限重试。长素材机制有合成数据测试，真实长素材效果未验收。

**难点三：异步之后仍要检查视频是否存在。** 独立审查提出“第一批请求过程中用户删除视频，后续批次仍继续调用”的情况。回归先观察到删除后仍完成，再补每批和完成前归属检查，阻止后续付费调用与孤立结果。任务提交后才执行、队列满时落库失败状态、服务重启后可明确重试，均有测试。

**可观测性：** 线程池任务不会自动继承原请求的追踪上下文，已显式绑定独立任务追踪，并在成功和失败时清理，避免统计漏记或混入下一任务。Token 仍是程序估算，不代替账单。

**原有总结的真实发现：** 短素材分析经过两轮、6 次模型调用才结束，Critic 仍未全部通过，页面保留人工核验警告。OCR 工具缺失时使用语音降级。由此不把“API 通了”与“内容全对”混为一谈，也没有为了截图去掉警告。

**验证：** 最终后端 159 项、前端 76 项与构建通过，独立复审通过。详细过程见《AI 智能选段 V1：实际验收记录》。新增功能与决策由 AI 辅助实施；本记录不编造用户亲自排查、上线给同学使用或性能提升经历。
