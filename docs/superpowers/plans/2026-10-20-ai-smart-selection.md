# AI 智能选段 V1 实施计划

> 执行方式：使用 executing-plans 按阶段推进，每阶段反馈结果。本计划已获用户批准，于 2026-10-20 开始执行；各阶段按实际证据勾选，不提交或推送 Git。

**Goal：** 用户上传视频并获得文字稿后，按自己的目标让 AI 推荐保留句段，预览和微调后导出 MP4。

**Architecture：** 复用现有上传、带时间转写、文字编辑器、方案保存和异步导出。新增“文字稿 → 推荐句段编号”的受限模型调用，由后端校验编号并映射真实时间；推荐结果经过用户确认才写入剪辑方案。

**Tech Stack：** 沿用 Spring Boot / Java 21、现有模型调用能力、Jackson、MySQL / MyBatis、Vue 3、FFmpeg。复用现有鉴权、任务执行与成本护栏，原则上不新增依赖。

**Spec：** 本对话已经讨论的“按目标自动选段 → 人工预览 → 导出”方案。用户随后确认执行，接口已按下面约定实现；实际结果见验收记录。

## 1. 当前基础与本轮边界

已经验证：百炼自动生成句段、文字定位、删除恢复、保存重开、MP4 导出下载。已有真实短合成素材验收，以及后端 139 项、前端 63 项测试和前端构建通过的基线。

本轮新增两项：

1. 配置硅基流动文本模型，实际验证原有总结与理解链路。
2. 增加 AI 智能选段，生成可解释、可修改的推荐方案。

首版保持原视频顺序、按整句段选择，不改写台词、不生成配音、不做多轨剪辑。仅根据文字判断与目标的相关性，不能宣称识别了画面、表情或动作中的精彩瞬间。

同济回放平台接入不纳入本计划。暂不做上传后无人确认就直接导出的流程。

## 2. 用户最终怎么用

上传视频 → 自动转写 → 点击“AI 智能选段” → 填写剪辑目标 → 等待推荐 → 查看保留理由、预计时长并预览 → 应用推荐 → 手动微调 → 保存并导出。

示例目标：“保留完整的英语交流，去掉等待和无关内容，尽量保留问答前后文。”

这里的“完整”是模型选择目标，需要人工检查，不是系统能保证的识别精度。没有合适片段时允许返回“未找到”，不能为了出片随意选择。

## 3. 按阶段实施

### 阶段一：真实 AI 总结联调

- [x] 用户把硅基流动 Key 配置到被 Git 忽略的本地 `.env`；不发聊天、不写前端、不上传 GitHub。
- [x] 核对现有模型配置、模型权限与实际调用涉及的服务；若还需要 Embedding 或 OCR，明确说明，不能假定一个聊天模型 Key 就能覆盖所有服务。
- [x] 使用已有自制素材和已有时间轴生成总结，检查内容是否对应原视频、证据时间是否合理、前端是否完整展示。
- [x] 确认复用已有 ASR 文档；检查失败时是否可理解、是否有有限重试，避免重复识别与无上限调用。
- [x] 记录真实运行结果、模型名称和待补配置；不把返回 HTTP 200 当作内容正确。

**交付：** 原总结链路的真实验收结论；若仍受其他服务配置限制，单列阻塞，不冒充全部验收。

### 阶段二：定义选段协议，先把后端规则做可靠

- [x] 新建 `editor/SmartSelectionModels.java`、`SmartSelectionValidator.java` 和对应测试，明确请求、推荐结果与校验错误。
- [x] 请求绑定 `mediaId`、`transcriptId` 和用户目标；后端先校验视频归属及字幕版本，再读取文字稿。
- [x] 给模型发送真实句段 ID、文字和必要上下文；模型只返回编号及理由，不接受模型提供的视频时间或下载地址。
- [x] 先写失败测试，再实现：不存在的 ID、跨字幕 ID、重复 ID、倒序、空结果、畸形 JSON、超长理由、无权限请求。
- [x] 后端按原时间轴排序去重，使用现有 `ClipRangePlanner` 计算实际区间和预计时长。无效 ID 拒绝，不静默猜测。

拟定的模型输出示例：

```json
{
  "selections": [
    {
      "cueIds": ["asr-8-1", "asr-8-2"],
      "reason": "保留开场与主题介绍，提供后续内容的上下文。"
    }
  ]
}
```

**交付：** 不依赖真实模型也能验证的选段规则。原字幕、原视频和已有剪辑方案均不被推荐请求修改。

### 阶段三：接入模型，处理长文字和异步任务

- [x] 新建 `editor/SmartSelectionService.java`、`SmartSelectionController.java` 及测试，复用已有模型客户端、用户鉴权和限流能力。
- [x] 拟定接口：`POST /media/editor/selections` 创建推荐任务，`GET /media/editor/selections/{id}` 查询状态及结果；状态为 QUEUED / PROCESSING / COMPLETED / FAILED。
- [x] 用新的 Flyway V5 迁移保存推荐任务、用户和字幕归属、目标、结果及错误码，不修改已执行的 V4。记录模型与提示词版本，便于复查。
- [x] 使用有界后台执行，模型调用不占数据库事务。活动任务重复提交复用；失败重试有次数上限，服务重启后遗留处理中任务转为可重试失败，不能永久等待。
- [x] 提示词要求按目标选择完整对话，保留必要前后句；字幕内容作为待分析材料，不能作为系统指令执行。
- [x] 先跑通短素材。长稿按句段分批，建议每批最多 100 句且文字不超过 12000 字符，相邻批重叠 2 句；模型上下文限制更小时降低上限。单句超限明确报错，不静默截断。
- [x] 合并各批推荐后统一校验、去重、排序；任一批失败不把局部结果标记为完整成功。首版不承诺精确控制最终时长，始终展示实际预计时长。
- [x] 为总批次、累计调用时间和重试设置预算；执行时依据所选模型确定配置，并写入验证记录。没有请求预算不得开展长稿真实调用。

**交付：** 可查询进度、可恢复查看的推荐任务。覆盖超时、模型格式错误、队列拒绝、重复请求、跨用户读取和分批边界的测试。

### 阶段四：把推荐接到现有编辑器

- [x] 修改 `client/src/editorApi.js`、`useTextVideoEditor.js`、`components/TextVideoEditor.vue`，添加目标输入、生成状态、推荐理由与“应用推荐”入口。
- [x] 页面展示推荐保留句段及预计时长，复用现有播放器检查结果；已有手动选段在用户确认应用前保持原样。
- [x] 应用推荐只更新当前编辑草稿；保存仍走现有版本校验，导出仍走现有 `ExportService`，不另写一套 FFmpeg 导出逻辑。
- [x] 推荐生成期间字幕或方案发生变化，应用前检测冲突，不能把旧版本推荐悄悄套到新方案。
- [x] 覆盖前端测试：关闭重开恢复状态、迟到结果不覆盖当前视频、失败可重试、空推荐、应用前后差异、手动修改与保存冲突。

**交付：** 用户能从真实推荐走到预览、应用、微调和导出，不新增只展示效果的假按钮。

### 阶段五：真实验收和文档更新

- [x] 短素材完整走一遍：自动转写 → 真实 AI 推荐 → 预览 → 应用 → 导出 → 下载并播放；检查是否删去目标内容、是否截断问答。
- [x] 用合成句段数据验证 205 句跨批、重叠去重和后续批次失败；不计作真实长视频验收。真实长素材与真人听感留为明确的后续验收范围。
- [x] 运行后端完整测试、`client` 目录的 `npm test` 与 `npm run build`，检查原手动剪辑、转写和导出无回归。
- [x] 实际截图放入 `docs/images`，README 说明新增能力与边界；验证记录包含素材、目标、模型、实际结果和失败情况。
- [x] 沿用 `docs/text-video-editor-decisions.md` 记录真实困难和选择，不把本计划中的预期难点写成已发生经历。

**完成标准：** 无预制推荐结果，使用真实模型选段；后端只接受有效句段；用户可以检查和修改方案；最终 MP4 内容和选段一致。真人识别、切点听感和长视频效果分别验收，不以自动化测试代替。

## 4. 优先记录的面试问题

| 问题 | 实施时记录的证据 |
| --- | --- |
| 为什么让 AI 返回编号，而不是时间？ | 无效编号被拦截、真实时间映射与区间计算的测试 |
| 怎样避免只有回答、没有问题？ | 实际被截断的例子、提示词调整及调整前后的结果 |
| 长视频文字放不进模型怎么办？ | 分批边界、重叠段去重、失败批次和真实调用预算 |
| AI 调用成功，为什么还不能直接导出？ | 协议校验、版本冲突、用户确认和方案快照 |
| 如何控制重复调用和费用？ | 活动任务复用、限流、有限重试和调用次数记录 |

每次按“现象 → 原因 → 可选方案 → 最终选择与代价 → 验证证据”记录，注明哪些由用户决定、哪些由 AI 辅助实施。没有实测不写“节省两小时”“准确率提升”等指标。

## 5. 用户需要配合的事情与反馈节奏

- 首先：配置硅基流动 Key；模型选择在核对账户权限后确定，不需要先充值或购买新服务。
- 后续：如有合适素材，提供一段不含敏感信息、允许上传语音与文字服务的口播或对话视频；没有素材时继续用自制合成内容验证机制，明确效果验收的局限。
- 在真实长稿调用前确认本次调用预算；不擅自批量消耗额度。
- 每阶段反馈：做完什么、真实结果、遇到的难点、下一步、是否需要用户操作。默认先完成一个可运行阶段，再继续下一阶段。

后续可再讨论“按目标选段后直接导出”，仍需复用同一套校验和快照机制。第一版先交付可解释、可修正的推荐，避免把不可靠的选择藏在“一键”里。
